# AI 新闻 Bot 结构化两阶段编辑流水线设计

日期：2026-07-23
状态：待用户书面审核
目标仓库：`bgu436475-ops/Baic-AI-Message-Bot`

## 1. 目标与非目标

### 1.1 核心目标

本次优化不追求新闻覆盖率，也不制作“AI 行业热榜”。唯一目标是：

> 最大化用户每分钟阅读所获得的决策价值、技术增量和可行动信息。

系统应优先回答以下问题：

- 今天具体发生了什么变化？
- 哪一类用户会受到影响，影响的是成本、能力、工作流还是业务指标？
- 证据在哪里，读者能否直接核查？
- 读者今天或未来 7 天内可以采取什么行动？
- 与过去 7 天已经推送的内容相比，新增信息是什么？

### 1.2 非目标

- 不保证每天固定输出 10 条。
- 不用低价值内容补足版面。
- 不把融资金额、行业观点或模糊趋势本身视为入选理由。
- 不让大模型直接决定最终排名、分榜或绕过硬门槛。
- 不在本次优化中改变 Cloudflare Worker、GitHub Actions 的触发时间和调度架构。

## 2. 总体架构

采用“结构化两阶段编辑流水线”：

```text
候选采集（约 80 条）
  → 规则粗筛（15–20 条）
  → 原文抓取与清洗
  → 模型提取结构化证据
  → 程序校验证据锚点
  → 程序执行硬门槛
  → 7 天事件级去重
  → 程序分项评分
  → 程序互斥分榜
  → 飞书卡片与网页数据输出
  → 写入事件历史与审计记录
```

职责边界如下：

| 模块 | 主要职责 | 是否允许决定入选 |
| --- | --- | --- |
| `collectors` | 从现有信息源收集约 80 条候选 | 否 |
| `shortlist` | 依据来源、时效、具体信号做低成本粗筛 | 否 |
| `source_fetcher` | 只抓取 15–20 条粗筛候选的原始页面 | 否 |
| `evidence_extractor` | 从原文中提取结构化事实与证据锚点 | 否 |
| `gatekeeper` | 执行不可绕过的硬门槛与强制淘汰规则 | 是 |
| `event_history` | 生成事件指纹并执行过去 7 天去重 | 是 |
| `scoring` | 用确定性规则计算分项分数与惩罚项 | 是 |
| `board_builder` | 按阈值与容量生成互斥榜单 | 是 |
| `reporter` | 生成 schema v3、网页数据和飞书卡片 | 否 |

大模型只负责理解原文和输出受约束的结构化字段。硬门槛、去重、计分、分榜和数量上限全部由程序决定。

## 3. 第一阶段：候选采集与规则粗筛

### 3.1 候选采集

延续现有来源体系，覆盖：

- 新模型与模型能力更新
- AI 编程
- Agent
- 图片与视频生成
- ComfyUI
- GitHub 开源项目
- MCP 与 Skill
- 重要行业、商业和监管动态

每次运行最多保留约 80 条标准化候选。候选至少包含：

- 标题
- 原始链接
- 来源名称与来源类型
- 发布时间
- 初步分类
- 原始摘要或正文片段

### 3.2 粗筛目标

粗筛只决定哪些候选值得付出原文抓取与模型分析成本，不决定最终入选。目标数量为 15–20 条。

粗筛信号包括：

- 来源是否可信，官方或一手来源优先。
- 是否在新闻时效窗口内。
- 标题或摘要是否包含版本、参数、价格、API、代码、基准、条款或业务指标。
- 是否命中目标主题。
- 是否明显属于强制淘汰类型。
- 是否与同批候选存在 URL、标题或实体级重复。

当合格候选不足 15 条时，不补入明显低价值内容；当高质量候选超过 20 条时，依据来源质量、时效和具体信号排序截断。

## 4. 第二阶段：原文核查与证据结构化

### 4.1 原文抓取

只对粗筛后的 15–20 条候选读取：

- 官方公告
- 论文
- 模型卡
- 代码仓库 README、Release 或文档
- 法案或监管原文
- 财报、投资者材料或公开业务数据
- 官方公开 Demo

抓取结果应保留：

- 最终 URL 与重定向链结果
- HTTP 状态和抓取时间
- 页面标题
- 清洗后的正文
- 可定位的标题、段落或列表块
- 抓取失败、登录墙、机器人限制或正文不足等状态

单条原文抓取失败不能导致整次任务失败。若全部候选原文都无法抓取，则属于系统性失败，任务应失败并允许备用运行重试，不能伪装成“今日无合格内容”。

### 4.2 原文不可访问时的例外

原文不可访问的条目：

- 不得进入“今日必看”。
- 不得进入“值得试用”。
- 只有同时满足以下条件时才可进入“观察项”：
  - 存在可信二手来源；
  - 二手来源包含可核查的具体事实；
  - 输出明确标记“原始来源暂不可核查”。

该例外不降低其他硬门槛，也不能作为填满观察项的手段。

### 4.3 结构化证据记录

模型必须为每条候选返回符合固定 schema 的 `EvidenceRecord`：

```json
{
  "candidate_id": "stable-candidate-id",
  "source_url": "https://example.com/original",
  "source_type": "official_announcement",
  "verification_status": "verified",
  "concrete_changes": [
    {
      "change_type": "price",
      "statement": "API 输入价格从 X 调整为 Y",
      "numbers": ["X", "Y"],
      "entities": ["Product API"]
    }
  ],
  "evidence_anchors": [
    {
      "quote": "用于程序核查的短文本",
      "locator": "Pricing / paragraph 2"
    }
  ],
  "affected_audience": ["API 开发者"],
  "affected_area": ["推理成本"],
  "recommended_action": ["重新计算现有调用量的月成本"],
  "event_entities": ["Company", "Product API"],
  "change_signature": "price-change",
  "scientific_claim": false,
  "policy_effective_date": null,
  "rejection_reasons": []
}
```

枚举值至少包括：

- `source_type`：
  - `official_announcement`
  - `paper`
  - `model_card`
  - `repository`
  - `law_or_regulation`
  - `financial_filing`
  - `official_demo`
  - `trusted_secondary`
- `verification_status`：
  - `verified`
  - `unavailable`
  - `blocked`
  - `insufficient`

模型输出解析失败时重试一次。再次失败则该次流水线按系统失败处理，避免用不完整结构生成新闻。

### 4.4 证据锚点校验

模型声称的每个主要具体变化必须至少关联一个证据锚点。程序需在清洗后的原文中确认锚点文本真实存在。

以下情况视为证据无效：

- 引文不存在于抓取正文。
- 引文只支持部分数字、实体或结论。
- 标题与正文中的数字、实体或版本冲突。
- 二手摘要中的结论无法在一手来源中找到。

证据锚点用于内部校验和审计。公开输出只展示简短事实摘要与原始链接，避免复制大段原文。

## 5. 硬门槛与强制淘汰

### 5.1 “今日必看”和“值得试用”共同硬门槛

每条内容必须同时满足：

1. 使用允许的一手来源，且 `verification_status=verified`。
2. 至少包含一个具体变化：数字、参数、价格、API、代码、模型、基准、条款或业务指标。
3. 至少有一个经程序验证的证据锚点。
4. 明确给出受影响对象。
5. 明确给出受影响内容。
6. 给出具体、可执行的建议行动。
7. 标题、正文、数字、实体和版本之间不存在冲突。
8. 重大科学结论存在原始论文或独立验证。
9. 未被过去 7 天事件级去重淘汰。

任何一项不满足，程序不得让模型绕过。

### 5.2 强制淘汰

以下内容直接淘汰：

- 只有融资金额，没有客户、收入、产品或技术数据。
- 只有行业观点，没有样本、案例或事实。
- 只有政策方向，没有具体条款和生效时间。
- 使用“有望、预示、推动、展示潜力”等表达，但没有对应证据。
- 标题和正文中的数字或实体发生冲突。
- 重大科学结论没有原始论文或独立验证。
- 与过去 7 天内容高度重复，且没有实质新增事实。

每次淘汰必须记录稳定的机器可读原因码及中文说明，例如：

- `funding_only`
- `opinion_without_evidence`
- `policy_without_terms_or_date`
- `vague_claim_without_evidence`
- `title_body_conflict`
- `scientific_claim_unverified`
- `duplicate_without_material_update`
- `missing_concrete_change`
- `missing_action`
- `invalid_evidence_anchor`

## 6. 过去 7 天事件级去重

### 6.1 事件指纹

去重对象是“事件”，而不只是 URL 或标题。事件指纹由以下标准化字段组成：

- 核心公司、组织或项目
- 产品、模型或仓库
- 变化类型
- 版本号或关键数字
- 生效日期或发布日期

示例：

```text
openai|model-x|api-price|v2|2026-07-23
```

### 6.2 判定顺序

1. 先检查完全相同的事件指纹。
2. 再检查核心实体重合度。
3. 再比较 `change_signature` 与关键数字、版本和日期。
4. 判断是否存在“实质新增事实”。

相同事件在以下情况下可作为更新保留：

- 新版本正式发布，而此前仅为预告。
- 价格、参数、基准或条款发生变化。
- 增加可用 API、代码、模型权重或 Demo。
- 公布新的生效时间、客户、收入或业务指标。
- 原始论文或独立验证补齐了此前缺失的证据。

保留的更新必须设置 `update_of`，摘要只描述新增部分，不能重复讲述完整旧事件。

### 6.3 历史状态

事件历史保存到 `.state/events.json`，至少记录：

- `event_fingerprint`
- 首次与最近出现时间
- 核心实体
- 变化签名
- 已推送的关键数字、版本和事实维度
- 所在榜单
- 原始链接

历史窗口为过去 7 个北京时间自然日。写入动作只发生在飞书发送成功后，防止发送失败却错误占用去重记录。

## 7. 确定性评分

总分 100 分：

| 维度 | 权重 | 判断重点 |
| --- | ---: | --- |
| 用户相关性 | 25 | 与目标读者的 AI 开发、产品、增长和决策工作是否直接相关 |
| 可行动性 | 20 | 是否存在 7 天内可执行的试用、升级、迁移、评估或风险动作 |
| 具体性 | 15 | 是否有明确数字、版本、参数、价格、代码、条款或业务指标 |
| 信息增量 | 15 | 相对过去 7 天是否增加新的事实维度 |
| 证据质量 | 15 | 一手来源、证据锚点和交叉验证质量 |
| 时间敏感度 | 10 | 是否存在发布、生效、迁移、价格或竞争窗口 |

模型只输出事实分类信号，程序用固定映射计算各项分数。所有分项分数和理由必须可测试、可追踪。

### 7.1 惩罚项

- 近似重复但只有轻微新增：`-20`
- 证据只覆盖部分主张：`-15`
- 存在明显营销夸大：`-10`
- 发布超过 72 小时且没有新的决策窗口：`-10`
- 同一公司当天已有 2 条入选：该公司的后续内容不得进入“今日必看”或“值得试用”

惩罚项在基础分之后计算，最低分为 0。

## 8. 互斥分榜

### 8.1 今日必看

- 最多 5 条。
- 总分不低于 75。
- 证据质量不低于 12/15。
- 信息增量不低于 10/15。
- 满足全部共同硬门槛。

### 8.2 值得试用

- 最多 3 条。
- 不得已进入“今日必看”。
- 总分不低于 62。
- 可行动性不低于 14/20。
- 必须存在可访问的模型、API、代码、Demo、升级或迁移路径。
- 建议行动必须能在 7 天内执行。

### 8.3 观察项

- 最多 3 条。
- 不得已进入前两个榜单。
- 已核查内容总分不低于 50；或符合“原文不可访问”的严格例外。
- 对例外内容明确标记“原始来源暂不可核查”。
- 不使用“值得持续关注”作为分析，必须说明待验证的具体事实。

三个榜单互斥。按分数、信息增量、证据质量、发布时间依次排序；仍相同则使用稳定的事件指纹排序，保证相同输入产生相同输出。

所有榜单都允许为空。系统不得为达到数量上限而降低阈值。

## 9. 输出数据与兼容性

### 9.1 Schema v3

`web/public/data/latest.json` 升级为 schema v3：

```json
{
  "schema_version": 3,
  "generated_at": "2026-07-23T09:05:00+08:00",
  "run_status": "published",
  "boards": {
    "must_read": [],
    "try_now": [],
    "watch": []
  },
  "items": [],
  "pipeline_stats": {
    "candidate_count": 80,
    "shortlist_count": 18,
    "source_verified_count": 15,
    "rejected_count": 7
  }
}
```

每个公开条目至少包含：

- `board`
- `title`
- `summary`
- `concrete_change`
- `affected_audience`
- `affected_area`
- `recommended_action`
- `evidence_url`
- `verification_status`
- `event_fingerprint`
- `score`
- `score_breakdown`
- `update_of`（如适用）

`items` 为三个榜单的扁平合集，暂时保留以兼容现有网页读取逻辑。网页逐步迁移为优先读取 `boards`。

### 9.2 内部审计文件

完整候选、抓取状态、证据锚点、分项评分和淘汰原因写入独立内部审计文件，不进入公开网页数据。

审计记录应能回答：

- 为什么某条进入或未进入榜单？
- 哪个硬门槛失败？
- 分数由哪些信号组成？
- 是否命中过去 7 天重复？
- 原文抓取和证据核查是否成功？

审计文件不得记录 API key、Webhook、签名密钥或完整受版权保护正文。

## 10. 飞书与网页呈现

### 10.1 飞书卡片

卡片按以下顺序展示：

1. 今日必看
2. 值得试用
3. 观察项

每条内容展示：

- 一句话具体变化
- 影响对象与影响内容
- 建议行动
- 证据链接
- 总分
- 必要的验证状态标签

主要分析禁止使用：

- “这对行业具有重要意义”
- “这展示了 AI 的巨大潜力”
- “这预示着未来的发展方向”
- “这可能推动相关应用”
- “值得持续关注”

必须用数字、变化、对象、证据和行动替代。

### 10.2 合法空榜

若流水线完整成功但没有条目通过硬门槛：

- `run_status=no_qualifying_items`
- 三个榜单和 `items` 都为空
- 飞书仍发送一次正常空榜卡
- 卡片文案为“今日无内容通过硬门槛”
- 附候选数量、已核查来源数量和主要淘汰原因统计
- 该次任务视为成功
- 写入每日发送守卫，备用任务不得重复发送

合法空榜与系统失败必须严格区分。

## 11. 失败语义与幂等

| 场景 | 处理 |
| --- | --- |
| 单个来源抓取失败 | 记录失败并继续 |
| 全部来源抓取失败 | 任务失败，允许备用运行重试 |
| 模型结构解析首次失败 | 使用同一输入重试一次 |
| 模型结构解析再次失败 | 任务失败 |
| 标题、正文、数字或实体冲突 | 淘汰条目并记录审计原因 |
| 流水线成功但零入选 | 发送合法空榜，任务成功 |
| 飞书发送失败 | 任务失败，不记录为已发送 |
| 飞书成功、网页发布失败 | 保留已发送记录，重试时不得重复发送飞书 |

每日幂等键由“北京时间日期 + 发送目标 + 摘要类型”组成。正式榜和合法空榜都使用同一每日发送守卫。

## 12. 测试策略

### 12.1 单元测试

- 粗筛数量为 15–20，并覆盖不足 15、超过 20 的边界。
- 原文抓取、清洗、超时、重定向和受限页面。
- 模型结构 schema 验证和一次重试。
- 证据锚点必须真实存在于抓取正文。
- 每一条硬门槛和强制淘汰原因。
- 事件完全重复、近似重复和实质更新。
- 六项评分、所有阈值和惩罚项。
- 三榜互斥、容量限制、稳定排序和不补位。
- 原文不可访问的观察项例外。

### 12.2 集成测试

- 从候选到 schema v3 的完整成功路径。
- 合法空榜与系统性失败的区别。
- 飞书三分榜卡片、部分空榜和全空榜。
- 网页读取 schema v3，同时兼容已有 schema v2。
- 飞书发送成功但网页发布失败时不重复发送。
- 正常主任务、主任务失败后的备用重试、合法空榜后的备用跳过。

### 12.3 验收条件

- Python 测试全部通过。
- Cloudflare Worker 测试全部通过。
- Web 构建与测试全部通过。
- 固定样本重复运行产生相同分数、顺序和分榜。
- 所有公开条目都能追溯到有效证据链接。
- 过去 7 天相同事件无实质新增时不会再次推送。
- 零入选时飞书正常收到空榜卡，任务状态为成功。

## 13. 实施边界与迁移顺序

后续实现计划应按可独立验证、可独立提交的增量展开：

1. 数据结构、审计原因码和 schema v3。
2. 粗筛与原文抓取。
3. 结构化证据提取与锚点校验。
4. 硬门槛。
5. 事件历史与 7 天去重。
6. 确定性评分与互斥分榜。
7. 飞书三分榜与合法空榜。
8. 网页 schema v3 展示与兼容。
9. Actions 幂等、失败语义和端到端回归测试。

## 14. 已确认的设计决策
